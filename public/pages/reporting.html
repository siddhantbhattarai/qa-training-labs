📝 QA Reporting Guide

Finding a bug is half the job. Reporting it well is the other half.

Anatomy of a great bug report

Answer four questions fast: What's wrong? How do I reproduce it? How bad is it? What did you expect?

FieldWhat goes here
ID / TitleUnique ref + one line: [area] what + where
EnvironmentDifficulty level, URL, browser, account
PreconditionsState needed before the steps
Steps to ReproduceNumbered, exact, repeatable
Expected ResultWhat should happen — cite the spec / Stable build
Actual ResultWhat did happen, with evidence
Severity / PriorityImpact + how soon to fix
EvidenceScreenshot, response body, logs
💡 Pro tip: run the same steps at X-QA-Level: stable — whatever the Stable build does is your "Expected Result". Airtight every time.

Worked example

ID:        BUG-014
Title:     Cart accepts quantity 0 when adding an item
Env:       Level=Low, http://localhost:3000, Chrome, user@qalab.com
Steps:     1. POST /api/cart/add { "productId": "<id>", "quantity": 0 }
           2. GET /api/cart
Expected:  Step 1 returns 400; item NOT added (verified on Stable)
Actual:    Step 1 returns 200; cart shows a line with quantity 0
Severity:  Medium     Priority: P3
Evidence:  response-bug014.json
Notes:     100% reproducible; also accepts negative quantities

Severity vs Priority

Severity = how badly it hurts the product. Priority = how soon to fix. They're independent.

SeverityLab example
CriticalOpen /api/seed/reset wipes the whole DB
HighRegister as admin; order charges stale price; stock never decremented
MediumQuantity 0 accepted; duplicate cart lines; 500 instead of 400
LowFloat noise in cart total; over-long name accepted

Practice loop

  1. Pick a feature + level (start Low).
  2. Write 3–5 test cases first (include negative & boundary).
  3. Execute; file a bug report for each failure.
  4. Switch up a level and retest — note fixes & new edge cases.
  5. Confirm "Expected" against Stable.
  6. Write a one-paragraph test summary.
